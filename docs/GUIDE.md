# 相关说明文字 · 项目通读

> 这一篇是**说明性文字**，不重复表格化的接口清单。目的是让第一次接手的人（或验收者）能顺着读下来，
> 明白「这个程序是什么、为什么长成这样、一次完整使用会发生什么、哪些地方故意不做」。
> 接口清单看 `README.md`，技术决策看 `ARCHITECTURE.md`，数据看 `VERIFICATION.md`，过程看 `DEVLOG.md`。

## 一、这个程序要解决什么

QQ 群里堆着一千多份大学资料，绝大多数是「能看到名字、但没保存到本地」的状态。以前的做法要么一次性把十几 GB 全拉下来，要么靠人肉翻聊天记录找文件，两种都不好用。

这个程序把这件事拆成两个完全不同的动作：**看**和**拿**。

「看」是只读的：只向 QQ 群文件接口要目录、文件名、大小、上传时间这些元数据，不碰文件内容。看完之后，所有文件先以「条目」的形式进入统一目录，按领域、科目、资源类型排好，界面上可以一层层点进去，一直点到单文件预览。「拿」则必须经过明确确认：你在界面上点下载、勾一批下载、或对某一类点整类下载，服务端才会去取直链把文件落到本地。

这样设计的原因是：未下载的文件本来就属于「授权可见」的范围，用户理应能浏览、能搜索、能问「有哪些」，但程序没有权力替用户决定把 12.73 GB 拉回硬盘。**看是免费的，拿是要授权的**，这条边界贯穿整个程序。

## 二、为什么是「一个新 Obsidian 库」

用户原本已经有一个 Obsidian 库。这次没有往里面加子目录，而是在桌面新建了「资源管理」目录，把它本身做成一个独立的 Obsidian 库。

理由有三条：第一，这个库里会放下载下来的 PDF、DOCX、ZIP 等原文件，混进原有笔记库会污染原有结构与搜索结果；第二，AI 插件、社区插件配置都是库级别的，独立库可以单独启用，不影响原有插件；第三，万一以后要重做或删除，直接删这个目录即可，原有笔记完全不动。

库里的东西分三处：`资源/` 放原文件，`笔记/` 放每个文件对应的预览笔记，`大纲/` 放一层层可点击的索引页（Obsidian 里叫 MOC）。最上面还有三篇 `00-` 开头的入口文档：总览、全量多级大纲、使用说明。每个大纲页都用 wikilink 连到下一级页面，最终连到单文件笔记，所以在 Obsidian 里也能像在网页里那样「学习 → 高等数学 → 真题试卷 → 某份 PDF」一路点下去。

## 三、一次完整使用会发生什么

启动 `start.bat` 时，程序先确保 Obsidian 库骨架和插件都在，然后做一次只读刷新。若 QQ 在线，就递归遍历三个群的所有文件夹，把元数据写进 `catalog.json`；若 QQ 掉线，就读取上次保存的离线快照，界面会明确写「离线快照」并锁住下载。**刷新这一步永远不会产生文件下载**。

接着程序为全部条目建立全文索引。这里有个刻意的设计：哪怕文件没下载，也会在索引里占一行，只不过正文是空的，只有标题、路径、分类等元数据。因此 AI 能回答「有哪些高数真题还没下载」，却绝不会假装读过那些文件的内容。

浏览器打开界面后，左栏是授权来源和分类树，中间是当前层级的下一级节点与文件列表，右栏是单文件预览和 AI 对话。点节点就往下一层钻，面包屑可以往回退。每份文件都有明确的状态徽标：绿色的「已下载」或橙色的「仅元数据 · 未下载」。未下载的点开预览，看到的只有文件名、群内路径、体积、分类和「尚未下载，无正文摘要」的说明，不会有一段编出来的内容。

当你确认下载时，服务端会再次检查确认标志、文件 id 白名单、扩展名白名单、离线状态和单批上限，然后才去 QQ 取直链。文件落地后依次发生：正文抽取、抽取式摘要、写预览笔记、更新目录状态、重建全文索引、重刷全部大纲页。所以下载完不用手动「导入」或「刷新索引」，界面与 Obsidian 里立刻就能看到新内容。

## 四、AI 是怎么保证不瞎编的

这套 AI 和「把整本文档丢给大模型」不是一回事。命中判定、相关度打分、源文件索引全部由本地 SQLite FTS5 检索完成，模型只负责把检索到的片段用中文简短说一遍。

具体有三道防线。第一道是**检索闸门**：问题拆成检索词后，若真正能在资料里出现的有效词不足，或者最高分低于阈值，直接返回「授权可见的资料中没有检索到相关信息」，连模型都不调用。所以「量子纠缠超导材料制备工艺」这种完全不相关的问题，8 毫秒就如实回绝了。

第二道是**数据等级标注**：给模型的上下文里，每条资料都带标签——「已下载·含正文」或「仅元数据·未下载·无正文」。后者明确写着「不要据此推测文件内容」。像「有哪些 / 多少份 / 未下载」这类问题干脆不交给模型数数，而是走目录的确定性统计，答案里一定带上「仅元数据，未下载，无正文摘要」。

第三道是**提示词硬约束**，来自试跑里一次真实的翻车：一份《微电子制造技术2026真题》原文只有选择题题干和 A–D 选项，没有答案，模型却按常识推断出「浸没式」。核对原文后发现这是臆造，于是在提示词里加了一条硬规则：若片段只是题目、选项、目录或清单，没有明确答案，就必须回答「资料只给出题目与选项，未给答案」，严禁用常识推断、也不许把选项罗列成结论。修复后这道题正确回绝。此外，如果模型自己误说「没有」，而检索闸门明明命中了，程序会改用本地原文摘录，保留命中状态和来源，不让模型一句话把已经找到的资料抹掉。

模型本身可配两种：默认的本机 Bonsai2 27B，或任意 OpenAI 兼容的外部 API。外部 API 的密钥只写在本机 `state/secrets.json`，不进仓库、不回显到界面。本地模型必须保持「关闭思考模式」，因为它是思考型模型，开着的话单问要几十秒到几分钟；关掉后约 2–4 秒。模型没启动也没关系，AI 会自动降级成纯本地摘录式回答，源文件索引照常给。

## 五、微信为什么没有做进去

这不是偷懒，是评估后确认做不到，而需求里也明确写了「不可行则明确限制，并仅先完成 QQ 导入的完整可视化界面」。

QQ 能接，是因为本机跑着 NapCat OneBot 11 协议端，它把 QQ 的群文件目录以 HTTP 接口暴露出来，程序可以递归遍历元数据、按 file_id 取直链。微信这边，本机是微信 4.x 客户端，没有 OneBot 或任何 Bot 协议端，个人微信也没有官方开放 API；聊天数据库是加密 SQLite，既读不到也不该读；`msg/file/` 目录里那 378 个文件是**已经落地到本地**的明文文件，只有文件名、大小、月份，看不到云端还没下载的文件、看不到是哪个群发的、看不到发送者。

也就是说，微信这边根本不存在「已授权可见但尚未下载」的元数据层，而这一层恰恰是本程序大半能力的基础。企业微信连接器确实存在，但那需要企业管理员 corpid/secret 与可见范围授权，属于另一套生态，也不等价于个人微信群文件。

因此界面上微信一栏明确显示「未接入」，并附一段可展开的限制说明，逐条列出「无登录方式 / 无云端未下载文件 / 无群归属 / 不读聊天库 / 仅可经显式授权只读扫描本地已落地文件 / 企业微信不对等」。代码里保留了 `lib/wechat.py` 这个适配器位置：只有当用户在配置里亲手填入授权目录并主动开启，才会只读枚举该目录下的文件名、大小、时间，而且绝不扫描任何 `.db`。这条路径默认关闭，也不会出现在界面上。

## 六、离线与降级说明

QQ 接口并不总是稳定。试跑里就遇到两次：一次是启动时 502，用 QQ MCP 的启动工具拉起后恢复；另一次是跑完之后服务掉线，重新拉起时 NapCat 要求扫码登录（二维码会放到桌面），说明登录态过期了。

程序对这两种情况的处理是一致的：刷新失败就回落到上次保存的元数据快照，界面标「离线快照」，**下载接口直接拒绝**。这样即使快照里的 `file_id` 已经失效，也不会拿去乱下载。恢复在线必须用户显式点「刷新来源」，程序不会自作主张把下载放开。同理，NapCat 重启后旧 `file_id` 失效导致 `real fileUUID not found!`，也是让用户刷新一次元数据即可，不需要重新确认任何东西。

还有一层运行时保护：每次接口请求都会实时探活，一旦发现 QQ 在运行中途掉线，会立刻把状态从 live 收紧为 snapshot 并锁定下载，避免界面还挂着「在线」的旧标记骗人。

其他降级都是「有就更好、没有也能用」：PyMuPDF 缺失时 PDF 只登记元数据；扫描版 PDF、老格式 doc/ppt/xls、zip 抽不出正文就明确标注原因；外部 API 超时或本地模型没起，AI 降级为摘录式回答；密钥错误只提示认证失败，不回显密钥。

## 七、目录里每个位置是干什么的（叙述版）

`server.py` 是唯一入口，所有网页请求和 API 都从这里进，顺带负责启动时的初始化与刷新。`lib/` 里，`catalog.py` 管那份唯一的目录文件，`classify.py` 决定一个文件属于哪个领域/科目/类型，`qq.py` 与 `wechat.py` 是两种来源的适配器，`download.py` 是把守确认闸门的那一层，`extract.py` 负责把各种格式变成可检索的文字，`index.py` 把元数据与正文写进 FTS5，`vault.py` 负责把目录翻译成一整棵 Obsidian 大纲和每篇预览笔记，`llm.py` 屏蔽本地模型与外部 API 的差异，`ai.py` 把检索、闸门、提示词、来源索引串成一次问答，`config.py` 管路径与密钥。

`web/` 是三栏界面，纯原生 HTML/CSS/JS，不需要构建工具。`obsidian_plugin/` 是部署进新库 `.obsidian/plugins/` 的右侧栏插件，连的是同一个本地服务。`tools/` 放两个脚本：离线引导和 GitHub 推送。`docs/` 是全部说明文档，`state/` 是运行时产物（目录、索引、正文、密钥），被 `.gitignore` 排除，**不会出现在 GitHub 上**。

## 八、维护与验收说明

后续改动按用户约定直接提交并推送到 `main`，提交信息用 `feat / fix / docs / refactor / test / chore` 前缀；重要里程碑打注附标签。改分类规则只需编辑 `config.json`，不需要动代码。所有脚本生成的笔记都带生成标记，重建时只覆盖这些，不碰手工写的内容。

验收时建议先看 `docs/RELEASE.md` 的逐项清单，再按「启动 → 逐级下钻 → 预览 → 三种下载 → 两类 AI 提问 → Obsidian 插件」的顺序走一遍。需要人工确认的主要是浏览器界面的目视效果（本次以 HTTP + API + 端到端链路验证为主，没有做 GUI 自动化点击），以及 QQ 重新扫码登录后点「刷新来源」能否恢复在线。

## 九、隐私与安全说明文字

服务只绑定 `127.0.0.1`，不对局域网或公网开放。QQ 的 OneBot 令牌从本机 NapCat 配置动态读取，既不写进项目也不写进日志；前端拿到的字段经过白名单过滤，`file_id`、令牌、本地缓存绝对路径都不会下发。程序不索要也不保存 QQ 账号密码，登录态由 QQ 客户端与 NapCat 自己管理。下载必须显式确认，程序从不主动把范围扩到全量。群里下载的资料、抽取的正文、外部 API 密钥都留在本地 `state/` 或桌面库中，不上传 GitHub。微信聊天数据库一律不读。
